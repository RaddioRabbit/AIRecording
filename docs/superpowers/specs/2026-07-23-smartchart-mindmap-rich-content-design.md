# 智能图表 v6：思维导图内容丰富化 + 图表缩放

日期：2026-07-23
状态：已确认设计（用户逐节批准）
前置：v5 统一思维导图 + 大纲编辑（`2026-07-22-smartchart-mindmap-editable-design.md`）

## 1. 背景与问题

v5 把所有内容类型统一到三级思维导图（root → 分支 → 要点），但用户反馈：**最多只能自动细化到二级，大部分只有一级**，只看图表无法明白、复述音频内容。

信息丢失发生在两处：

1. **`to_mindmap()` 映射丢字段**：LLM 提取的 plan 信息其实丰富（会议有背景/讨论要点/分歧/结论/行动项），但映射成导图时大量丢弃——会议只保留「结论 + 行动项」；随手记（memo）一级分支下完全没有要点。
2. **硬性规模守卫过紧**：每分支要点 ≤6、要点文字 >40 字截断、分支标题 >20 字截断，要点内容被砍成「标题党」。

另外用户提出两个图表查看体验需求：画布宽度应随页面变宽；可以放大、缩小图表（触控板 + 鼠标滚轮）。

## 2. 目标与非目标

**目标**

- 用户只看思维导图就能明白并复述音频内容：每个分支都有 3-10 条言之有物的要点，提取出的信息不再被映射丢弃。
- 图表支持缩放查看：触控板捏合、⌘+鼠标滚轮、工具条按钮三种方式。

**非目标（明确不做）**

- 不加第四层级（root → 分支 → 要点 → 子要点）。三级结构不变，靠「喂饱」而非「加深」。后续若不够再单独立项。
- 不做按窗口宽度的响应式重排（reflow）。等比缩放 + 缩放控制已覆盖可读性痛点；重排需要 resize 时反复调后端重渲染，代价大收益小。
- App 端大纲编辑交互不变（仍是改文字 + 增删节点，两级）。
- 后端渲染布局结构不变（左右两列、确定性几何），只调参数。

## 3. 设计 · 提取层（后端 skills）

**统一纪律**：所有类型的提取提示词增加一条——「覆盖原文所有关键信息，宁多勿漏；每条要点必须言之有物，带具体事实、数字、人名、结论，禁止空话」。

各类型提取上限与 `to_mindmap()` 映射调整：

| 类型 | 提取上限（现 → 新） | 映射进导图的要点（现 → 新） |
|---|---|---|
| meeting | 要点 1-4 条 → **2-6 条**（每条 ≤60 字）；分歧 0-2 → **0-3** | 仅结论+行动项 → **背景 + 全部讨论要点 + 分歧 + 结论 + 行动项** |
| lecture | 要点 1-3 条 → **2-5 条**（每条 ≤60 字） | 要点+概念 → **全部要点 + 全部概念（名称：解释）** |
| dialogue | 关键信息点 0-2 条 → **1-4 条**（每条 ≤50 字） | 摘要+信息点 → **摘要 + 全部信息点** |
| speech | 要点 0-3 条 → **1-5 条**（每条 ≤60 字） | 摘要+要点+金句，结构不变、要点更多 |
| interview | 回答要点 1-3 条 → **2-5 条**（每条 ≤70 字） | 要点+金句+标签，结构不变、要点更多 |
| memo | 每条要点仅一句话，无子节点 → **每条要点增加一条 ≤60 字展开说明** | 无子节点 → **每条要点下挂 1 条展开说明** |

同步上调各 skill `normalize`/`merge` 中的 `MAX_*` 常量（如 `MAX_POINTS_PER_TOPIC`、`MAX_ANSWER_POINTS` 等），保证长录音分块提取后合并不再砍回去。memo 的 plan schema 需为要点增加可选 `detail` 字段（pydantic 模型同步）。

**贯穿纪律不变**：LLM 只产 JSON；segment_ids 必须真实；金句逐字校验；`numbers_have_evidence` 数字一致性校验全部保留，防止「为凑数量编内容」。

**代价**：LLM 输出变长，生成耗时与 token 成本上升约 20%-40%。

## 4. 设计 · 渲染层（后端 mindmap.py）

仅参数调整，`guard_mindmap_doc` / `layout_mindmap` 结构不变：

- 每分支要点上限：6 → **10**（超出截断 + 「还有 N 项」节点逻辑保留）
- 要点文字截断：40 → **80 字**
- 分支标题截断：20 → **28 字**
- 分支数上限 **8 不变**（8 个分支已铺满左右两列）
- 要点换行行数上限：3 → **6 行**（右列 19 字/行 × 6 ≈ 114 字容量，覆盖 80 字上限；左列 15 字/行同理）
- 块高度公式 `block_height` 已按行数动态计算，行数上限提高后自动适配
- 画布宽 1200pt 不变；图变高后 WebView 纵向滚动；PNG 导出为整页截图，长图完整导出

**编辑回路一致性**：`/chart/render` 端点走同一个 `guard_mindmap_doc`，用户编辑后的重渲染自动套用新上限。

**效果预估**：8 分支 × 平均 6 要点的录音，图高约从现在的一屏增长到 2-3 屏，信息量约 3 倍。

## 5. 设计 · 缩放与宽度自适应（App 端）

**宽度自适应**：保持 SVG `width="100%"` + viewBox 的等比缩放现状（窗口多宽图多宽），不做重排。

**缩放控制**（`ChartWebView.swift` + 图表头部工具条）：

- `webView.allowsMagnification = true`：触控板双指捏合缩放
- **⌘ + 鼠标滚轮**缩放：本地事件监听 `.scrollWheel`，按住 ⌘ 时调节 `webView.magnification`（`setMagnification(_:centeredAt:)`，以鼠标位置为中心）；不按 ⌘ 时滚轮保持滚动长图的默认行为
- 图表头部（「导出 PNG」旁）加三个小按钮：**− ／ 缩放百分比 ／ ＋**，步进 0.25，范围 0.5x–3.0x，点百分比复位 100%
- 放大后图超出可视区由 WebView 内部滚动查看
- 导出 PNG 前强制 `magnification = 1.0` 再整页截图，导出后恢复用户当前缩放，保证导出完整尺寸原图

**后端零改动。**

## 6. App 端其他影响

零改动。导图三级结构、DTO、大纲编辑、编辑持久化（v6 前置已实现 `mindMapJSON` 落盘）全部兼容——本次只是节点文字更长、要点更多，Swift 侧无冲突上限。

## 7. 测试（全在后端 `ChartAgent/tests/` + App 缩放逻辑）

- 各 skill 测试：更新为新上限；新增「`to_mindmap` 不丢字段」断言（会议背景/分歧必须出现在 children；memo 要点必须带展开说明）
- `test_mindmap.py`：守卫测试更新（10 要点截断 + 「还有 N 项」、80 字截断、28 字分支标题）；布局测试更新行数上限 6
- `test_mindmap_render_endpoint.py` / `test_mindmap_pipeline.py`：端到端走一遍，渲染产物通过结构校验
- 新增丰富度回归测试：构造多主题转写 + 桩 LLM 确定性数据，断言生成的 MindMapDoc 每个分支 children ≥ 3
- App 端：缩放步进/范围钳制逻辑抽为可测的纯函数（或 ViewModel 方法），补单测

## 8. 回退方案

提示词与守卫参数都是独立常量，提取质量下降时可单独回调提示词，不涉及结构改动；`numbers_have_evidence` 与守卫的拦截能力不变。缩放为纯增量功能，不影响既有渲染与编辑链路。
