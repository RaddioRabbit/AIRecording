# Word 导出纪要：序号修复 + 围栏剥离 + 真正的 Word 排版

日期：2026-08-04
状态：已确认（用户口头批准设计）
涉及文件：`AIRecording/Services/DocxExportService.swift`

## 背景与问题

「AI 纪要」在 App 页面内显示正常，但「导出 Word」生成的 docx 有两个问题：

1. **序号错误**：「关键讨论要点」部分的有序列表序号不是从 1 开始，而是从该列表第一行在整篇纪要中的行号开始（用户截图中从 14 开始）。
2. **裸露的代码围栏**：当 LLM 返回的纪要外层包了 ```` ```markdown ```` 代码块标记时，围栏行（```` ```markdown ```` 和结尾的 ```` ``` ````）被原样输出到 Word 文档中，显示为两行多余文字。

页面显示正常是因为页面走的是 `MarkdownTextView` / `MarkdownBlockParser` 的渲染路径，与导出逻辑无关。

## 根因

`DocxExportService.buildDocumentBody(summary:recording:)`（`AIRecording/Services/DocxExportService.swift:124`）逐行解析 markdown：

- 第 172 行生成有序列表序号时使用了**行索引** `i+1` 作为序号，而不是列表内的计数。列表前面有任何内容（标题、日期、其他章节），序号都会跟着偏移。
- 解析循环不认识 ```` ``` ```` 代码围栏行，围栏行落入「普通段落」分支被原样输出。

## 设计

只改 `DocxExportService.swift`，不动页面渲染、不动数据存储、不改 LLM 提示词。

### 1. 有序列表序号：列表内独立计数

在 `buildDocumentBody` 的解析循环中增加一个局部变量 `orderedListCounter: Int = 0`：

- 遇到**有序列表项**（`isOrderedListItem` 为真）：`orderedListCounter += 1`，输出 `\(orderedListCounter). \(text)`。
- 遇到**任何其他行**（空行、标题、无序列表项、普通段落、围栏行）：`orderedListCounter = 0`。

效果：每个连续的有序列表块都从 1 开始编号，与页面显示一致；同篇纪要中多个有序列表互不影响。

不使用 markdown 原文中的序号（即使原文是 `1.`），统一用计数器重编号——这样即使 LLM 原文编号有跳号/重复，导出的 Word 也是干净的连续序号。

### 2. 剥离 markdown 代码围栏

在解析循环开头（空行判断之后）增加围栏行识别：trimmed 行以 ```` ``` ```` 开头（包括 ```` ```markdown ````、```` ``` ```` 及任意 ```` ```xxx ```` 语言标记）时，**跳过该行**（不输出任何段落），`i += 1` 继续。

效果：无论围栏出现在纪要的什么位置（开头/结尾/中间），都不会进入 Word 文档。同时有序列表计数器在遇到围栏行时重置为 0（围栏属于「非有序列表项」）。

不剥掉围栏内的内容——围栏内是正经纪要正文，正常解析。只跳过围栏标记行本身。

### 3. 真正的 Word 排版（新增需求，用户 2026-08-04 追加）

现状：导出的 docx 没有 `styles.xml`，`w:pStyle` 引用的 Title/Heading1 等样式在 Word 里找不到定义，全部退化成默认正文；行内的 `**加粗**`、`*斜体*` 标记被原样输出（星号可见）。用户要求导出的 Word 呈现真正的 Word 排版效果而非 markdown 原始符号。

改动（仍只动 `DocxExportService.swift`，生成的 docx 结构随之扩展）：

1. **新增 `word/styles.xml`**：定义 `Title`（大字号加粗）、`Subtitle`（灰色小字）、`Heading1`/`Heading2`/`Heading3`（递减字号加粗）、`Normal`、`ListParagraph`（基于 Normal + 左缩进 720 twips、悬挂缩进 360 twips）。同时在 `[Content_Types].xml` 注册 styles 的 Override，并新增 `word/_rels/document.xml.rels` 声明 document → styles 的关系。
2. **行内格式解析**：`makeParagraph` 改为把文本按 `**bold**` 和 `*italic*`（含 `__bold__`、`_italic_`）拆成多个 run，加粗 run 带 `<w:b/>`、斜体 run 带 `<w:i/>`，标记符号本身不输出。解析用简单的顺序扫描，不支持嵌套；无法配对的多余星号按普通文字原样输出（不丢字）。
3. **列表呈现不变**：项目符号仍用「• 」文本前缀、有序列表用「N. 」文本前缀（配合 ListParagraph 的悬挂缩进，换行对齐整齐）。不引入 numbering.xml。

效果：标题有真实标题样式（大字号加粗），加粗/斜体显示为真格式、星号消失，列表缩进整齐。

### 4. Markdown 表格转 Word 原生表格（新增需求，用户 2026-08-04 二次追加）

现状：纪要中的 GFM 管道表格（如「待办事项」的 `| 事项 | 负责人 | 截止日 |`）在导出时被当作普通段落原样输出，Word 里显示为满屏 `|` 和 `---` 符号。页面渲染（`MarkdownBlockParser.parseTable`）本来就支持表格，只有导出路径缺失。

改动（仍只动 `DocxExportService.swift`）：

1. **表格识别**：`buildDocumentBody` 中，trimmed 行以 `|` 开头且下一行匹配分隔行模式（`^\|?\s*:?-+:?\s*(\|\s*:?-+:?\s*)+\|?$`）时，收集后续所有 `|` 开头的连续行作为一个表格块，生成 `<w:tbl>`，之后追加一个空段落（Word 要求表格与后续内容之间有段落）。以 `|` 开头但没有分隔行的行不算表格，按普通段落原样输出。
2. **表格样式**：整表 100% 页宽（`tblW 5000 pct`），四边及内部 `single sz=4 color=999999` 细边框，单元格四向内边距（上下 60、左右 108 twips）；列宽平均分配（页面正文宽 8306 twips ÷ 列数）。表头行单元格加粗（forceBold）+ 浅灰底色 `F2F2F2`。
3. **单元格内容**：复用行内解析（`makeRunsXML`），单元格内 `**加粗**` 同样转真加粗；对齐符号行（`:---:`）忽略，统一左对齐。
4. **健壮性**：数据行格子数少于表头时补空、多于表头时截断，导出永不因表格行不规整而失败。

## 不做的事（YAGNI）

- 不引入真正的 Word 自动编号（numbering.xml）——继续用纯文本序号，改动最小。
- 表格不支持：单元格内换行、合并单元格、按内容自适应列宽、转义管道符 `\|`。
- 不处理 markdown 图片、链接、嵌套列表、代码块样式（纪要内容目前不包含，本次不扩展）。
- 不改 `MarkdownTextView` / `MarkdownBlockParser` 页面渲染（页面显示正常）。
- 不修改已存储到 Core Data 的纪要原文。

1. `swift build` 编译通过。
2. `swift test` 现有测试不回归。
3. 手动验证：用问题录音（新录音 8，纪要带 ```` ```markdown ```` 围栏、关键讨论要点 7 条）导出 Word，确认：
   - 「关键讨论要点」序号为 1–7；
   - 文档中不出现 ```` ```markdown ```` / ```` ``` ```` 行；
   - 各级标题为大字号加粗的真实标题样式；
   - `**xxx**` 显示为加粗文字，星号不出现；
   - 其他章节（参与人项目符号、会议主题段落）格式正常、列表缩进整齐；
   - 「待办事项」表格显示为带边框的真表格，表头加粗灰底，不出现 `|` / `---` 文本。
4. 边界情况：纪要中无围栏、无有序列表、无加粗标记时导出结果与修复前一致；星号不配对的行不丢字；表格行格子数不规整时不报错；单独一行 `|` 文字不误判为表格。
